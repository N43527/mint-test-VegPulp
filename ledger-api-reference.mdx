# Ledger Payments API

Welcome to the **Ledger** Payments API.  This page is the complete reference for every endpoint,every field and every error code you will meet while integrating.It is long on purpose: we would rather you find the answer here than open a support ticket. - test 3

> The API is served over HTTPS only.  Plain HTTP requests are rejected with a `400` and never reach the application servers. Requests are limited to **100** per second per key.

<Info>
  All timestamps are Unix epoch seconds.   All amounts are integers in the smallest unit of the currency (cents,pence,yen).
</Info>

## Base URL

```text
https://api.ledger.dev
```

Sandbox requests go to the same host.The API key decides the mode:

- keys that start with `sk_test_` hit the sandbox
- keys that start with  `sk_live_` move real money

- keys that start with `rk_` are restricted keys with a subset of permissions
  - you create them in the dashboard
  - they can not create payouts

## Authentication

Pass your secret key in the `Authorization` header using the Bearer scheme.<br />Never ship a secret key in a browser or a mobile app.

```bash
curl https://api.ledger.dev/v1/payments \
  -H "Authorization: Bearer sk_test_51H..."
```

<Warning>
  Rotate a key immediately if it leaks.  Old keys keep working for  **24 hours** after rotation so that in flight deploys do not break.
</Warning>

<Steps>
  <Step title="Create an account">
    Sign up at [dashboard.ledger.dev](https://dashboard.ledger.dev)   and verify your email.
  </Step>
  <Step title="Grab a test key">
    Open **Developers** → **API keys** and copy the key that starts with `sk_test_`.

    <Tip>
      You can create as many test keys as you like.  Name them after the service that uses them.
    </Tip>
  </Step>
  <Step title="Make your first request">
    Run the cURL command above.   You should see an empty list:

    ```json
    {  "data": [],
       "has_more": false }
    ```
  </Step>
  <Step title="Go live">
    Replace the test key with a live key and flip the _Live mode_ toggle in the dashboard.
  </Step>
</Steps>

## Idempotency

Every `POST` accepts an `Idempotency-Key` header.   We store the first response for 24 hours and replay it for any retry that carries the same key.

1. generate a UUID v4 per logical operation
2. send it on the first attempt
3. reuse it on **every** retry of that operation
4. never reuse it for a different operation

| Scenario | What happens |
| --- | --- |
| same key, same body | original response is replayed |
| same key, different body | `409 idempotency_key_reused` |
| key older than 24h | treated as a new request |

<AccordionGroup>
  <Accordion title="Why 24 hours?">
    It is long enough to survive an incident and short enough that keys do not pile up.
  </Accordion>

  <Accordion title="Can I choose my own key format?">
    Yes.Anything up to 255 characters.UUIDs are just a convention.
  </Accordion>

  <Accordion title="Do GET requests need a key?">
    No.   Reads are naturally idempotent and the header is ignored.
  </Accordion>
</AccordionGroup>

<Tabs>
  <Tab title="Node">
    ```javascript
    const payment = await ledger.payments.create(
      { amount: 1999, currency: 'usd' },
      { idempotencyKey: crypto.randomUUID() }
    );
    ```
  </Tab>
  <Tab title="Python">
    ```python
    payment = ledger.Payment.create(
        amount=1999, currency="usd",
        idempotency_key=str(uuid.uuid4()))
    ```
  </Tab>
  <Tab title="Ruby">
    ```ruby
    payment = Ledger::Payment.create({amount: 1999, currency: 'usd'}, idempotency_key: SecureRandom.uuid)
    ```
  </Tab>
</Tabs>

## Errors

Ledger uses conventional HTTP status codes.   Codes in the `2xx` range mean success,`4xx` means you sent something we could not accept and `5xx` means we broke.

| Status | Meaning |
| --- | --- |
| 200 | Everything worked |
| 201 | Object created |
| 400 | The request was malformed,   see `message` |
| 401 | No valid API key |
| 402 | The request was fine but the payment failed |
| 404 | The object does not exist or belongs to another account |
| 409 | Idempotency conflict |
| 429 | Too many requests,  slow down |
| 500 | Our fault.Retry with backoff |

The error body always has the same shape:

```JSON
{
  "error": {
    "type":    "card_error",
    "code": "card_declined",
    "message": "Your card was declined.",
    "param": "source"
  }
}
```

_Tip:_ the `param` field tells you which request field caused the problem, when there is one.

## Create a payment

{/*  TODO(payment): rewrite this intro before launch  */}

`POST`   `/v1/payments`

Creates a new payment intent and reserves funds on the customer card. The request is idempotent when you send an Idempotency-Key header, and retries within twenty four hours return the original response instead of creating a second payment.

<ParamField path="amount" type="integer" required>
  The amount to charge,in the smallest unit of the currency. Must be at least 50 and no more than 99999999.
</ParamField>

<ParamField path="currency" type="string" required>
  Three-letter ISO code.    Lowercase.
</ParamField>

<ParamField path="customer" type="string">
  ID of an existing customer. When omitted the payment is created as a guest payment and no payment method is saved.
</ParamField>

### Request

<CodeGroup>

```bash cURL
curl -X POST https://api.ledger.dev/v1/payments \
     -H "Authorization: Bearer sk_test_123" \
     -H 'Content-Type: application/json' \
     -d '{"amount": 1000, "currency": "usd"}'
```

```javascript Node
const ledger = require('ledger')('sk_test_123');
const payment = await ledger.payments.create({
    amount: 1000,
    currency: 'usd',
});
console.log(payment.id)
```

```python Python
import ledger
ledger.api_key = "sk_test_123"
payment = ledger.Payment.create(amount=1000, currency="usd")
print(payment.id)
```

</CodeGroup>

### Response fields

| Field | Type | Description |
| --- | :-: | --- |
| id | string | Unique identifier of the payment. |
| amount | integer | Amount in the smallest currency unit.  Cents for USD. |
| currency | string | Three letter ISO currency code,lowercase. |
| status | enum | One of  `pending`, `succeeded`, `failed` or `canceled`. |
| metadata | object | Up to 50 key value pairs that you control. |
| created | timestamp | Unix epoch seconds when the object was created |

<ResponseField name="id" type="string">
  The identifier.Store it,you will need it for refunds and disputes.
</ResponseField>

<ResponseField name="status" type="enum">
  - `pending` :  waiting on the customer
  - `succeeded`: funds captured
  - `failed`  : declined by the issuer,see `failure_code`
</ResponseField>

<Note>
  Test mode payments never move real money. Use the card number 4242 4242 4242 4242 with any future expiry and any CVC to simulate a successful payment, or 4000 0000 0000 0002 to simulate a decline.
</Note>

**Common failure codes**

1. `card_declined` -- the issuer refused the charge
2. `insufficient_funds`--   the customer does not have enough balance
3. `expired_card` --the card expiry date is in the past
4. `processing_error` -- something went wrong on our side,  retry with the same idempotency key

- retries are safe
- do **not** change the amount between retries

1. `authentication_required` -- 3DS challenge needed

## Webhooks

Ledger sends a `POST` to your endpoint whenever something interesting happens.   Respond with any `2xx` within 10 seconds or we retry with exponential backoff for  **3 days**.

<AccordionGroup>
  <Accordion title="payment.succeeded">
    Fired once funds are captured.   The payload contains the full payment object.
  </Accordion>

  <Accordion title="payment.failed">
    Fired when the issuer declines.`failure_code` explains why.
  </Accordion>

  <Accordion title="refund.created">
    Fired when a refund is created,before the money reaches the customer.
  </Accordion>

  <Accordion title="dispute.opened">
    Fired when a card network opens a chargeback.   You have 7 days to submit evidence.
  </Accordion>

  <Accordion title="payout.paid">
    Fired when a payout lands in the merchant bank account.
  </Accordion>
</AccordionGroup>

### Verifying signatures

1. read the `Ledger-Signature` header
2. split it on `,` into `t=` and `v1=` parts
3. compute `HMAC_SHA256(secret, t + "." + raw_body)`
4. compare with `v1` using a constant time comparison
   - reject if the timestamp is older than 5 minutes
   - reject if the signatures differ

```javascript
const expected = crypto.createHmac('sha256', secret).update(`${t}.${body}`).digest('hex');
if (!crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(v1))) throw new Error('bad signature');
```

## Rate limits

- [x] 100 requests per second per API key
- [ ] burst allowance of 500 requests (coming soon)
- [x] `429` responses include a `Retry-After` header

When you get a `429`,  back off.  Do not retry in a tight loop; you will only make it worse and we will eventually block the key for an hour.
